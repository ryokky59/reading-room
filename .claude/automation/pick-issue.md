# Pick up one `auto` Issue (steps for the Orca automation)

Orca starts this every 15 minutes in a fresh worktree from `origin/main`, only when `precheck.sh` passes. The owner is not there. Follow `CLAUDE.md`, except where this file says otherwise. Do not wait for the owner: where the Issue, a comment or an agent's report recommends an option, take it and carry on to the merge, as `CLAUDE.md` 「Decisions」 says. Stop for the owner only for the reasons there (no recommended option, a step that cannot be undone, something only the owner can give). Write comments to the owner in Japanese.

## Labels

- `auto`: the planner (or the owner, or step 1 below) found a recommended way to build it and nothing that cannot be undone. Only these are picked up, `idea` or not.
- `in-progress`: being worked on, as in `CLAUDE.md`. On an `auto` Issue it means this automation is working on it.
- `auto:blocked`: stopped for the owner, for a reason in `CLAUDE.md` 「Decisions」. When they answer and remove it, the Issue is picked up again (their answer is in the comments).

## Steps

1. **Pick**: from `gh issue list --repo ryokky59/reading-room --state open --label auto`, take the lowest-numbered one without `auto:blocked` or `in-progress`. Only one. Read its body and all comments. If none is left, look at the open `idea` Issues without `auto`, `auto:blocked` or `in-progress` (and not `report`), lowest number first: give each that has a recommended option `auto` and `ready` (`gh issue edit <n> --add-label auto --add-label ready`), and stop each that has none as in step 4 (adding `auto` with `auto:blocked`, so it is not read again every run). Then pick from `auto` again; if still none, go to step 8.
   A question to the owner in the body or comments (オーナーに決めてほしいこと, 「どちらにするか」) that nobody answered is not a stop when it comes with a recommendation: take the recommended option, and say on the Issue in one line which one you took before developing. Only when step 4 already holds before any development (no recommendation, or a step that cannot be undone), stop that Issue as in step 4 and pick the next one in the same run, until one can be developed or none is left. Stopping the run at the first only makes the next run, 15 minutes later, read the next one and stop again (#131: #68 and #77 both had open questions).
   First look at `main`'s latest finished CI run (`gh run list --repo ryokky59/reading-room --branch main --status completed --limit 1`). If a newer run on `main` is still in progress, wait for it first (`gh run watch <id> --exit-status`): it tests the commit this run branches from, and a failure the next run does not repeat is a flaky test, which gets a planner Issue in step 6 and does not stop development (#120: the #157 merge failed on `board.spec.ts:698`, the #158 merge passed 11 minutes later). If it failed, a PR from this run cannot pass its checks either: pick the `auto` Issue about the failing test instead of the lowest-numbered one. If there is none, have the `planner` draft it (step 6), write the failing test on it, and go to step 8 without developing.
2. **Develop**: start one `developer` agent (Agent tool, subagent_type `developer`, no worktree isolation: this worktree is already yours) with the Issue number and `E2E_PORT=3401`. Tell it the owner is away: where it would stop and report, it should report to you instead, with its recommended option; you take that option and send it on (SendMessage) unless step 4 holds. Tell it too that it may not connect to the production database. If an open PR for the Issue already exists (an earlier run stopped partway; `gh pr list --repo ryokky59/reading-room --search "Closes #<n>"`), do not start a new branch: tell the developer to continue that PR, or go straight to step 3 when its comments say only the review is left. A run that has to stop before step 8 for a reason other than step 4 writes on the Issue what is done and what is left, and removes `in-progress` so a later run picks it up.
3. **Review**: when it reports a PR, start a `reviewer` agent with the PR number and `E2E_PORT=3403`. If the reviewer asks for changes, send them back to the same developer (SendMessage), then review again. At most two rounds.
4. **Stop for the owner** only when one of these holds. A choice that comes with a recommendation (from the Issue, the developer, the reviewer or the planner) is not one of them: take it, write on the Issue which option you took, and carry on.
   - There is no recommended option: the Issue is vague or contradicts the code and nobody suggested a reading, or there are several options and none is marked as the one to take. When you can see which one is best yourself, that is a recommendation: write it and why on the Issue and take it.
   - A step cannot be undone: the PR's migration drops a table or column, or deletes or rewrites rows; the Issue needs a delete or overwrite in production data outside a migration; anything else whose loss a revert does not bring back.
   - It needs what only the owner can give: a secret's value, a login (`npx neonctl auth`), a Vercel setting or a paid plan you cannot change.
   - The reviewer still says 直してほしい after two rounds, or the checks cannot be made to pass. A check that fails on a test the PR did not touch is re-run once at most: a second failure means `main` is flaky, and more runs only spend CI time (#126: three runs, three different unrelated failures).

   Write a comment on the Issue (and on the PR, if there is one): what you found, which reason above holds, and the options with what each would do. Then `gh issue edit <n> --add-label auto:blocked --remove-label in-progress` and go to step 8. Leave an open PR open.
5. **Merge** when all of these hold. If one does not, stop as in step 4: the PR stays open for the owner. Do step 6 before going to step 8: the findings are known now, and a list in a comment is not an Issue (#111: three findings waited in a comment until the owner's answer came).
   - The reviewer's latest 判定 is マージしてよい.
   - `gh pr checks <PR> --watch` ends with every check passing (CI and Vercel).
   - Nothing in the PR cannot be undone. A migration under `drizzle/` that only adds (a table, a nullable column or one with a default, an index) is fine; one that drops, renames, narrows a type, or deletes or rewrites rows stops (read the SQL, not only the file name). Changes to `package.json` dependencies, `.claude/automation/` or `CLAUDE.md` merge like anything else.
   - What only a real phone or the Vercel preview can show does not stop the merge, even when it is a 完了条件. A 完了条件 that names its check (an `@mobile` E2E test) and passed it is met; the rest (Safari's edge swipe, the notch, a look on the preview) goes in a PR comment after merging, under オーナーに確かめてほしいこと, one line each (#77: the PR waited a day for the owner, who said to merge without the check).

   Then `gh pr merge <PR> --merge`, `gh issue edit <n> --remove-label in-progress` (closing does not remove it), and `git push origin --delete <branch>` (`--delete-branch` merges but then exits 1 in a worktree, where `main` is checked out elsewhere, and leaves the remote branch). Merging deploys to production. Wait until the Vercel status on the merge commit is no longer pending (`gh pr view <PR> --json mergeCommit`, then `gh api repos/ryokky59/reading-room/commits/<sha>/status`); `commits/main` may already be another PR's merge (#139: #137 was merged seconds later, and `main` showed its deploy). If it failed, comment on the PR so the owner sees it.
   **Migration**: when the PR added files under `drizzle/`, apply them to production once the deploy is Ready, from this worktree on the merge commit (`git fetch origin main && git checkout --detach origin/main`):
   `DATABASE_URL="$(npx neonctl connection-string main --project-id round-feather-65545481)" npx drizzle-kit migrate`
   Never print the connection string or keep it in a file. Then check that production recovered: the new tables or columns are there (`echo "select column_name from information_schema.columns where table_name = '<table>'" | node .claude/scripts/reading-data.mjs`), and production has no new runtime errors since the deploy (Vercel MCP `get_runtime_errors` when you have it). Write on the PR what you applied and what you checked. If `neonctl` asks for a login, the migration fails, or production still errors, write it on the PR and the Issue at once with what is wrong and what the owner should do (`npx neonctl auth`, or reverting the merge), and say so in the closing lines of step 8: production may be broken until it is fixed.
6. **Follow-ups**: if the developer or reviewer left one (a same-cause path, an out-of-scope finding), have the `planner` draft it as an Issue. Per its rules it gets `auto` whenever it has a recommended way to go. When the planner instead writes a question for the owner with no recommendation on another open `auto` Issue, add `auto:blocked` to that Issue in the same run: left as it is, the next run picks it, stops at step 1 and asks the same thing again (#132: a question written on #114 after the owner's answer, labels unchanged, was found only when #114 was picked).
7. **Retro**: run the `retro` skill with the PR number. Merge its process PR (`retro-<issue>-<slug>`) once its checks pass (the same commands as step 5). Leave it open for the owner, with a comment saying why, only when it changes app code (that needs an Issue), or removes one of the stops in step 4 or in `CLAUDE.md` 「Decisions」 for a step that cannot be undone.
8. **Close**: check that `git status` is clean and every change is pushed or merged. Write two or three lines on what you did, then run as the very last command `/Applications/Orca.app/Contents/Resources/bin/orca worktree rm --worktree current --force`. It removes this worktree and this terminal, so nothing runs after it. If something is left (an unpushed change), do not close; write what is left on the Issue instead.

## Never

- Push to `main`, or merge anything other than the PRs step 5 and step 7 allow.
- Develop more than one Issue in a run. Issues stopped at step 1 without development do not count.
- Connect to the production database other than to apply a merged PR's migration and check it (step 5), or run `vercel env pull`. Delete or overwrite production data. The agents you start may not connect to production at all: say so in each one's prompt, the planner's too (#77: the planner read the production activity log to weigh a follow-up).
- Apply a migration before its PR is merged, or one that step 5 would not merge.
- Remove `auto` from an Issue, or change labels other than `auto` (adding it, in step 1), `in-progress`, `ready` and `auto:blocked`.
