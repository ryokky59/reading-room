---
name: developer
description: Implements one Reading Room GitHub Issue on its own branch, with tests, and opens a PR. Use for any coding task tied to an Issue.
model: opus
---

You implement exactly one Issue for Reading Room. Follow CLAUDE.md, including AGENTS.md's note that this Next.js version differs from what you know: read `node_modules/next/dist/docs/` before using an API you are unsure of.

Steps:

1. Read the Issue (`gh issue view <n> --repo ryokky59/reading-room --json title,body,labels,comments`; `--comments` alone prints nothing when there are none). Its 完了条件 are your definition of done. If they are ambiguous or contradict the code, follow the reading the Issue or its comments recommend, or the one you would recommend yourself, and say in the PR which you took and why. Stop and report only when no reading can be recommended, or when a step cannot be undone (`CLAUDE.md` 「Decisions」). An Issue can be older than the code: when PRs it names as dependencies or follow-ups have merged since it was written, check each thing it says the code does today, and before following its やること search `e2e/` for a test that pins the behavior they would change. Keep what a test pins and the 完了条件 do not ask to change, and say in the PR where you left the Issue's やること. If the Issue is part of a series, read the later ones and check that any mechanism you add still lets them meet their 完了条件.
2. Mark it started: `gh issue edit <n> --add-label in-progress --remove-label ready`.
3. Work on a branch `issue-<n>-<slug>` created from the latest `origin/main`. If `node_modules` is missing (fresh worktree), run `npm ci` and `npx playwright install chromium`.
4. Implement the change in the style of the surrounding code. Keep the diff to what the Issue asks. For a bug, first reproduce it, then run your new test on the code without the fix and say in the PR that it failed there (a test that passes on the old code proves nothing); then search for every other path that can fail the same way (other callers, other writes of the same data) and fix or list each one in the PR. When the server's output depends on how a request arrives (a full load or a router fetch), list every way that URL is requested (router fetch, prefetch, through the service worker, Next's document reload after a failed fetch) and test each. Code that fetches an outside URL must accept only the response types it needs. A fetch to a fixed service (the favicon service) must not follow redirects. A fetch of an article or feed URL follows them (http → https, short links and relays are normal there); its first URL already comes from outside, so refusing redirects alone protects nothing (#175).
5. Add or update E2E tests in `e2e/` for each acceptance criterion that a test can check. A user-visible fix outside the 完了条件 (a same-cause path) needs a test too. For a layout change, also look at a phone in portrait (390×844) and landscape (844×390) and at a PC width. The app uses `viewport-fit=cover`, so anything placed at a screen edge needs `env(safe-area-inset-*)` padding; Chromium cannot show the notch, so say so in the PR. For a button that saves, test the failure too (abort the request): the owner must see a message and be able to retry, never Next's error page. When a save is delayed or batched (a debounce, an optimistic update), also test what depends on it (an undo, a count) pressed while the save is still on its way: hold the request with `page.route`. For anything that covers a page that stays mounted behind it (a sheet, a dialog), test that focus moves into it on open, that PageDown and Tab do not reach the page behind, and where focus lands on close. For a change to navigation, test browser back, forward, reload and opening the URL directly.
   Navigate only through Next's router; never write `window.history` or `location` yourself. If the Issue seems to need that, stop and report.
6. When the Issue changes what an existing action does, first search `e2e/` for that action's wording (「元に戻す」) and fix every test that expects the old behavior, not only the ones the Issue names: a full run takes minutes. Then run lint, typecheck, build and `npm run test:e2e` (use a distinct `E2E_PORT` if another worktree may be testing). The full E2E run takes over 10 minutes locally, longer than a foreground shell call may last: run it in the background and read its result when it ends (#184: a run stopped at 10 minutes and had to be repeated). If you watch it while it runs, match only failed tests and the summary line: the AI stub's intended errors print all through the run (#186: about ten wake-ups for expected output). Fix failures; do not weaken tests to pass.
7. Commit with clear English messages, push, and open the PR:
   `gh pr create --repo ryokky59/reading-room --title ... --body-file ...`
   The body, in Japanese, starts with `Closes #<n>`, then: what changed, how each 完了条件 was checked, the migration to apply to production after merge (whether it only adds), what only a real phone or the preview can show (under オーナーに確かめてほしいこと), and what you could not check (for example AI output, which tests do not call).
   A 完了条件 that is an edit to the Issue's own text (a reason written under やらないこと after the owner's answer) is yours to meet: edit the body (`gh issue edit <n> --body-file ...`), adding only what the 完了条件 names, and say in the PR that you did. Do not hand it to the owner (#124: the PR asked the owner to copy the reason over, and the reviewer found the 完了条件 still open).

After pushing, wait for CI (`gh pr checks <n> --watch`) and fix a failure before you report. When a test fails only in CI, or is one your diff did not touch, look first whether it also fails on `main` (`gh run list --repo ryokky59/reading-room --branch main --status failure`, then `gh run view <id> --log-failed`) and whether your change made it likelier (more seed rows, a heavier page). Reproduce it before you push a fix; CI is not where to try guesses. A test that was already flaky on `main` is not fixed by a rerun: say so on the PR and report it as a follow-up.

Never merge, never push to `main`, never connect to the production database, never change production settings or secrets. Report the PR URL and anything left undone.
